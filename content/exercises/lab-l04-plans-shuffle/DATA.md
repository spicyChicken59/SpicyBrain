# Data dictionary and provenance

All data is synthetic and original. Cinderline Components is a fictional
manufacturer; the plants, lines and quantities are invented. No customer,
employer or product data is used.

## fixtures/inspections.json (skewed feed) and inspections_balanced.json

One object per inspection event, in a deterministic shuffled order.

| Field | Type | Meaning |
|---|---|---|
| `event_id` | string | `e0000`–`e0239`; unique per row; also the salt input |
| `plant` | string | `North`, `South` or `West` |
| `line` | string | `L1`–`L3`, uniformly random |
| `inspected_units` | integer | uniform 5–60 |
| `defective_units` | integer | uniform 0–min(4, inspected) |

Generated by `fixtures/generate_inspections.py` with `random.Random(seed)`:
seed **20260923** for the skewed feed (North 180, South 36, West 24 rows) and
seed **20260924** for the balanced feed (80/80/80). Regenerating writes the
same bytes; `run_tests.py` asserts that the committed files equal the
generator's output.

## expected/totals.json — derivation

Produced by `expected/derive_expected.py`, plain Python only (no PySpark, no
import of the solution): loops over the fixture rows and accumulates
dictionaries. `run_tests.py` re-runs that derivation in memory and asserts the
committed file is identical, so the literals cannot drift from the fixtures.

| Key | How it is derived |
|---|---|
| `row_count` | number of fixture rows |
| `defective_rows` | rows with `defective_units > 0` |
| `plant_totals` | per plant: row count, sum of inspected, sum of defective |
| `region_totals` | per region via plants.json: row count, sum of inspected |
| `hot_plant`, `hot_plant_rows`, `hot_share` | the plant with most rows; its rows; rows ÷ row_count rounded to 4 places |
| `hot_plant_line_counts` | rows of the hot plant per `line` |
| `salted_groups`, `max_salted_group_rows` | per `(plant, salt)` with `salt = zlib.crc32(event_id.encode()) % 4` — the same standard CRC-32 Spark's `crc32()` computes |
| `input_slices` | the four input partitions under the premise below: rows, rows per plant, rows kept by `defective_units > 0`, regions present |
| `grouped_partial_rows` | Σ over input slices of the plants present: one partial row per plant per partition |
| `regional_partial_rows` | Σ over input slices of the regions present |
| `dimension_rows` | plant rows with a non-null key (what a sort-merge join shuffles from the dimension) |
| `join_shuffle_read_rows` | `row_count + dimension_rows`: a sort-merge join shuffles every row of both inputs |

**The one premise.** `SparkContext.parallelize(rows, 4)` cuts a Python list into
four contiguous, equal slices in list order (positions 0–59, 60–119, 120–179,
180–239). The `input_slices` literals follow from that premise. The premise is
not taken on trust: test 02 reads the actual partition membership back from
Spark (`spark_partition_id()` per plant) and asserts it equals the derived
slices, so a different slicing would fail that test for the stated reason.

Recorded values for the skewed feed: 240 rows, 187 with defects; North
180/5898/336, South 36/1391/79, West 24/961/46; inland 180 rows/5898, coastal
60 rows/2352; hot share 0.75; North by line L1 64, L2 63, L3 53; largest salted
group 47. Input slices (North/South/West): 44/9/7, 42/11/7, 45/10/5, 49/6/5,
keeping 47, 48, 45 and 47 defective rows. Hence 12 grouped partial rows, 8
regional partial rows, 3 dimension rows and 243 rows read by a sort-merge join.

## expected/plans.json — derivation

Hand-written predictions from the rules the module teaches:

- A shuffle boundary (`Exchange`) appears wherever rows must meet by key:
  grouped aggregation (1), each input of a sort-merge join (2) plus any later
  aggregate (1), a window partitioned by key (1), a `repartition(n)` (1).
- Each shuffle `Exchange` closes the stage below it, so a job has one more
  stage than it has shuffle exchanges (the sort-merge query: 3 exchanges, 4
  stages). The fact side has 4 input partitions, the dimension 1, and every
  stage that reads a shuffle has `spark.sql.shuffle.partitions = 4` tasks when
  adaptive execution is off.
- A broadcast join replaces the fact-side exchange with a `BroadcastExchange`
  built by a separate job over the small side.
- `explain()` plans without starting a job.
- With adaptive execution on, coalescing merges the four tiny shuffle
  partitions into one, so the final stage runs one task and the result has one
  partition; unknown input statistics make the initial join plan a sort-merge
  join and measured sizes switch it to a broadcast join.

The first ten entries were written before any run. The `adaptive_skew_join`
entry names Spark's own operator vocabulary (`SortMergeJoin(skew=true)`, an
`AQEShuffleRead` marked `skewed`); it was written after a probe run showed how
Spark 4.0.4 prints them. Those strings come from Spark, never from the solution
under test. Where a run could differ between executions (which partition id a
key lands in, which side adaptive execution broadcasts), the tests assert
properties and record the observation instead.

## What the tests prove and do not prove

Proved for Spark 4.0.4, `local[2]`, four shuffle partitions: operator
structure, exchange counts, executed stages and task counts, shuffle records
per stage and per task, partition membership properties, exact rows and
totals, the raised guard, and that adaptive execution's broadcast build side
is a runtime outcome that can change between identical runs. Not proved: any
duration, memory, spill, network or behaviour on another version or on a
cluster. Shuffle bytes are recorded as observations and never asserted: they
depend on compression and row encoding.
