<!-- section:why -->

A data lead says, “We do not have the team to run another platform.” A feature response misses the concern. Understand what risk the person is protecting against.

<!-- section:understand -->

An objection can reveal a requirement, a past failure, a resource constraint, or a misunderstanding. Restate the concern neutrally, ask for the concrete cause, and connect the answer to a decision. Do not assume reluctance means lack of technical understanding.

For fictional Cinderline, a small team may reasonably resist a design that requires continuous support, unfamiliar skills, or two reporting paths indefinitely. Ask which responsibilities create the burden: source changes, identity administration, failed runs, cost management, or metric support. Then compare reducing scope, using a simpler cadence, bringing qualified delivery help, or retaining the current path.

A useful response can change the proposal. If the customer has no operating owner, a smaller pilot or a pause may be more defensible than another reassuring product claim. Make any service or partner contribution conditional on an actual agreement; do not promise someone else's support capacity.

<!-- section:see -->

**Fictional objection-to-evidence map.**

| Concern | Clarifying question | Possible response to test |
|---|---|---|
| Too much to operate | Which tasks have no owner? | Smaller cadence/scope; explicit operator |
| We already own a warehouse | Which need is unmet today? | Improve current path or coexist |
| Migration is risky | Which report must never be unavailable? | Parallel run and rollback |
| Cost is unpredictable | Which usage drivers vary? | Measured pilot and spending bounds |

Each response is a hypothesis to validate, not a script that automatically resolves the concern.

<!-- section:deeper -->

Avoid arguing with a customer's reported history. If a prior project failed, ask what conditions caused the failure and how the new proposal differs in verifiable ways. If the concern is contractual, legal, or a formal security commitment, involve the authorized owner. Technical plausibility does not give you authority to promise terms. Capture disagreement accurately in the decision record rather than editing it into agreement.

<!-- section:customer -->

For the data lead: “The operating burden is a real design constraint. Which responsibilities are hardest for your team to cover? We can compare a smaller scheduled scope, qualified delivery support, and improving the existing path before recommending another commitment.”

<!-- section:try -->

Write a response to the fictional statement “We already have a warehouse, so this is duplication.” Include a neutral question, a credible coexistence or retain option, and an evidence step.

<!-- section:revisit -->

A useful response: “Which reporting and integration needs does the current warehouse already meet, and which remain difficult? We may be able to improve the current path or introduce only the missing capability while retaining trusted reports. Let us map one quality workload and compare duplication, migration effort, and operating cost before recommending a change.”

The response neither concedes nor dismisses the concern. It makes duplication measurable and lets the architecture become smaller if the evidence supports that choice.
